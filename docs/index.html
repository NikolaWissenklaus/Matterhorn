Matterhorn v1 Coleta de eventos no Google Cloud

Visão geral

Matterhorn

O Matterhorn registra o que acontece no seu site (visualizações de página, cliques, compras) e grava cada evento no BigQuery do seu projeto no Google Cloud. É a mesma ideia do GA4 ou do Mixpanel, mas os dados, o esquema e a conta são seus.

Como funciona

São três peças. Um script no site monta o evento, um serviço no Cloud Run recebe e padroniza, e o BigQuery guarda. Toda a infraestrutura é criada pelo Terraform.

  1. O matterhorn.js junta o nome do evento, os parâmetros e o contexto da página (URL, título, navegador, dispositivo, idioma) e faz um POST em /mhc.
  2. O app.py valida o JSON, converte event_params para o formato do GA4 e insere a linha no BigQuery.
  3. A linha pode ser consultada poucos segundos depois.

O formato de event_params

No navegador, os parâmetros são um objeto comum. No BigQuery, viram uma lista de pares chave e valor, com o valor na coluna do seu tipo. É exatamente o layout do export do GA4.

Enviado pelo site
{
  "event_name": "add_to_cart",
  "event_params": {
    "item_id": "SKU-123",
    "quantity": 2,
    "price": 49.9,
    "gift": false
  }
}
Gravado no BigQuery
"event_params": [
  { "key": "item_id",  "value": { "string_value": "SKU-123" } },
  { "key": "quantity", "value": { "int_value": 2 } },
  { "key": "price",    "value": { "double_value": 49.9 } },
  { "key": "gift",     "value": { "string_value": "false" } }
]

A vantagem de copiar o GA4: quem já consulta o export do GA4 reaproveita as mesmas consultas com UNNEST, e as duas fontes podem ser cruzadas na mesma análise.

Componentes

tracker/matterhorn.js
Script instalado no site. Envia um page_view ao carregar e expõe matterhorn_event() para o resto.
backend/app.py
Serviço Flask com uma rota, POST /mhc. Roda no Cloud Run com gunicorn.
backend/Dockerfile
Imagem Python 3.10 slim. O build acontece no Cloud Build, sem Docker local.
infra/
Terraform do dataset, da tabela, da service account, do serviço e das permissões.
infra/schemas/events_raw.json
Esquema da tabela, separado do código para ser lido e revisado com facilidade.

O que cabe na v1

Esta primeira versão resolve a coleta. O resto fica para depois, de propósito.

IncluídoFora, por enquanto

Guia

Implantar o Matterhorn

Do projeto vazio no Google Cloud até o primeiro evento no BigQuery. Os comandos são para Ubuntu; no Windows, eles rodam dentro do WSL2.

Antes de começar

  • Um projeto no Google Cloud com faturamento ativo.
  • Papel de Owner no projeto, ou permissão para criar service accounts e conceder papéis no IAM. Editor não basta para a parte de IAM.
  • Uma cópia deste repositório na sua máquina.

Observação: em todos os comandos, troque SEU_PROJETO pelo ID do projeto, como meu-projeto-123. O ID aparece no seletor de projetos do console e é diferente do nome.

1. Preparar o ambiente

No Windows, tudo roda no Subsistema Windows para Linux. Assim as ferramentas se comportam igual a um servidor Linux e não conflitam com o que já está instalado.

  1. Instale o WSL2

    Abra o PowerShell como administrador e execute:

    PowerShell
    wsl --install

    Reinicie o computador se for pedido. Depois abra o Ubuntu pelo menu Iniciar e crie seu usuário e senha.

  2. Atualize o sistema e instale o Python

    O Python só é necessário para rodar o backend localmente. O build de produção acontece no Cloud Build.

    bash
    sudo apt update && sudo apt upgrade -y
sudo apt install python3 python3-pip python3-venv -y

2. Instalar gcloud e Terraform

  1. Google Cloud CLI

    bash
    sudo apt-get install apt-transport-https ca-certificates gnupg curl -y
curl https://packages.cloud.google.com/apt/doc/apt-key.gpg \
  | sudo gpg --dearmor -o /usr/share/keyrings/cloud.google.gpg
echo "deb [signed-by=/usr/share/keyrings/cloud.google.gpg] https://packages.cloud.google.com/apt cloud-sdk main" \
  | sudo tee -a /etc/apt/sources.list.d/google-cloud-sdk.list
sudo apt-get update && sudo apt-get install google-cloud-cli -y

  2. Terraform

    bash
    wget -O- https://apt.releases.hashicorp.com/gpg \
  | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt-get update && sudo apt-get install terraform -y

  3. Confira as versões

    bash
    gcloud --version
terraform version   # 1.5 ou mais novo

3. Configurar o projeto

  1. Autentique

    O primeiro login é o do gcloud. O segundo gera as credenciais que o Terraform usa.

    bash
    gcloud auth login
gcloud auth application-default login
gcloud config set project SEU_PROJETO

  2. Habilite as APIs

    bash
    gcloud services enable run.googleapis.com artifactregistry.googleapis.com \
  cloudbuild.googleapis.com iam.googleapis.com bigquery.googleapis.com

  3. Crie o repositório de imagens

    bash
    gcloud artifacts repositories create matterhorn-repo \
  --repository-format=docker --location=us-central1

4. Gerar a primeira imagem

Na raiz do repositório, envie a pasta backend/ para o Cloud Build. Ele executa o Dockerfile e publica a imagem no Artifact Registry.

bash
gcloud builds submit backend \
  --tag us-central1-docker.pkg.dev/SEU_PROJETO/matterhorn-repo/matterhorn-api:v1

Use tags crescentes (v1, v2, v3). A tag é o que diz ao Terraform qual versão deve estar no ar.

5. Criar a infraestrutura

  1. Preencha as variáveis

    bash
    cd infra
cp terraform.tfvars.example terraform.tfvars

    Só duas são obrigatórias. As demais têm padrão e estão descritas na referência.

    hclinfra/terraform.tfvars
    project_id = "SEU_PROJETO"
image_tag  = "v1"

  2. Revise e aplique

    bash
    terraform init
terraform plan
terraform apply

    O plan deve listar 6 recursos para criar. Confirme o apply com yes. No fim aparecem os outputs:

    Saída
    cloud_run_url         = "https://matterhorn-backend-xxxxxxxxxx-uc.a.run.app"
collector_endpoint    = "https://matterhorn-backend-xxxxxxxxxx-uc.a.run.app/mhc"
events_table          = "SEU_PROJETO.matterhorn_dataset.events_raw"
service_account_email = "matterhorn-cr-sa@SEU_PROJETO.iam.gserviceaccount.com"

Guarde o terraform.tfstate. Ele fica em infra/, fora do Git, e é por ele que o Terraform sabe o que já existe. Sem o arquivo, o próximo apply tenta criar tudo de novo e falha com "already exists".

6. Instalar o tracker

Abra tracker/matterhorn.js e coloque o collector_endpoint no ENDPOINT:

JavaScripttracker/matterhorn.js
var ENDPOINT = "https://matterhorn-backend-xxxxxxxxxx-uc.a.run.app/mhc";

Depois carregue o script em todas as páginas. As opções (HTML direto ou Google Tag Manager) estão na aba Tracker.

7. Verificar

Abra o site em uma aba anônima e rode no BigQuery:

SQL
SELECT event_name, url, browser, device, TIMESTAMP_MILLIS(timestamp) AS quando
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
ORDER BY timestamp DESC
LIMIT 10;

Pronto: se o seu page_view aparece no resultado, a coleta está funcionando. Se não aparece, veja Solução de problemas.

Guia

Enviar eventos com o tracker

O matterhorn.js tem cerca de 100 linhas, não depende de nenhuma biblioteca e é escrito em ES5, então roda em qualquer navegador e dentro do Google Tag Manager sem ajuste.

Instalar

Com o ENDPOINT preenchido, escolha uma das formas:

HTML
<!-- No <head> de todas as páginas -->
<script src="/js/matterhorn.js" defer></script>
Tag de HTML personalizado
<script>
  /* cole aqui o conteúdo inteiro de tracker/matterhorn.js */
</script>

No GTM, crie uma tag do tipo HTML personalizado com o acionador All Pages e publique o contêiner.

Configurar

As duas constantes ficam no topo do arquivo.

ConstantePadrãoPara que serve
ENDPOINTURL de exemploEndereço de coleta, terminado em /mhc. Vem do output collector_endpoint.
DEBUGfalseCom true, escreve no console cada evento enviado e o resultado.

Eventos personalizados

O page_view sai sozinho quando o script carrega. Para o resto, chame matterhorn_event(nome, params):

JavaScript
// Clique em um botão
document.querySelector("#assinar").addEventListener("click", function () {
  matterhorn_event("click", { button_id: "assinar", section: "hero" });
});

// Item adicionado ao carrinho
matterhorn_event("add_to_cart", { item_id: "SKU-123", quantity: 2, price: 49.9, currency: "BRL" });

// Compra concluída
matterhorn_event("purchase", { transaction_id: "T-9087", value: 199.8, currency: "BRL" });

Use nomes em snake_case e, quando existir, o mesmo nome do evento recomendado do GA4 (sign_up, add_to_cart, purchase). Assim as consultas servem para as duas bases.

Depurar

  1. Troque DEBUG para true e recarregue a página. O console mostra [matterhorn] enviando e, em seguida, gravado ou falhou.
  2. Na aba Network do DevTools, filtre por mhc. Cada evento gera um POST, às vezes precedido de um OPTIONS (o preflight do CORS).
  3. Compare o status com a tabela de respostas.

Exemplos

Consultar os dados no BigQuery

Todos os eventos ficam em uma única tabela. As consultas abaixo cobrem o que se costuma olhar primeiro. Troque SEU_PROJETO pelo ID do projeto ou use o output events_table do Terraform.

Eventos por dia

O timestamp é epoch em milissegundos. O fuso vai no DATE(); sem ele, o dia vira em UTC.

SQL
SELECT
  DATE(TIMESTAMP_MILLIS(timestamp), 'America/Sao_Paulo') AS dia,
  event_name,
  COUNT(*) AS eventos
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
GROUP BY dia, event_name
ORDER BY dia DESC, eventos DESC;

Páginas mais vistas

SQL
SELECT
  page_title,
  REGEXP_REPLACE(url, r'[?#].*$', '') AS pagina,
  COUNT(*) AS page_views
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
WHERE event_name = 'page_view'
  AND TIMESTAMP_MILLIS(timestamp) >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
GROUP BY page_title, pagina
ORDER BY page_views DESC
LIMIT 20;

Lendo event_params

Cada parâmetro é lido com uma subconsulta sobre UNNEST(event_params), igual ao GA4:

SQL
SELECT
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'button_id') AS button_id,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'section') AS secao,
  COUNT(*) AS cliques
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
WHERE event_name = 'click'
GROUP BY button_id, secao
ORDER BY cliques DESC;

Quando a consulta lê muitos parâmetros, funções temporárias deixam o SQL mais curto:

SQL
CREATE TEMP FUNCTION param_str(params ANY TYPE, nome STRING) AS (
  (SELECT value.string_value FROM UNNEST(params) WHERE key = nome)
);

SELECT
  param_str(event_params, 'item_id') AS item_id,
  COUNT(*) AS adicoes
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
WHERE event_name = 'add_to_cart'
GROUP BY item_id
ORDER BY adicoes DESC;

Valores numéricos

Um número pode estar em int_value ou em double_value, dependendo de ter casas decimais. Some as duas:

SQL
SELECT
  DATE(TIMESTAMP_MILLIS(timestamp), 'America/Sao_Paulo') AS dia,
  COUNT(*) AS pedidos,
  ROUND(SUM((
    SELECT COALESCE(value.double_value, value.int_value)
    FROM UNNEST(event_params) WHERE key = 'value'
  )), 2) AS receita
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
WHERE event_name = 'purchase'
GROUP BY dia
ORDER BY dia DESC;

Navegadores e dispositivos

SQL
SELECT
  device,
  browser,
  COUNT(*) AS page_views,
  ROUND(100 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS pct
FROM `SEU_PROJETO.matterhorn_dataset.events_raw`
WHERE event_name = 'page_view'
GROUP BY device, browser
ORDER BY page_views DESC;

Custo das consultas

A tabela não é particionada, então toda consulta lê as colunas citadas em todas as linhas, mesmo com filtro de data. Com pouco volume isso não pesa: o nível gratuito do BigQuery cobre 1 TiB de consultas por mês.

  • Selecione só as colunas necessárias. SELECT * lê a tabela inteira.
  • Confira a estimativa de bytes no editor do BigQuery antes de rodar.
  • Para painéis que rodam toda hora, grave o resultado numa tabela agregada por dia.

POST /mhc

Recebe um evento por requisição e grava uma linha em events_raw. Aceita qualquer origem (CORS aberto) e não exige autenticação.

bash
curl -X POST "https://matterhorn-backend-xxxxxxxxxx-uc.a.run.app/mhc" \
  -H "Content-Type: application/json" \
  -d '{
    "application_type": "web",
    "event_name": "teste_curl",
    "timestamp": 1789080479736,
    "event_params": { "origem": "terminal", "tentativa": 1 }
  }'

O corpo é lido como JSON mesmo com outro Content-Type, o que permite enviar com navigator.sendBeacon. Todos os campos são opcionais, mas qualquer campo fora do esquema faz o BigQuery recusar o evento inteiro.

Respostas

Operação

Operar e atualizar

Como publicar versões novas do backend, voltar atrás, acompanhar logs e resolver os problemas mais comuns.

Publicar uma nova versão

Toda mudança em backend/ segue o mesmo ciclo: gerar a imagem com uma tag nova e apontar o Terraform para ela.

  1. Gere a imagem

    bash
    gcloud builds submit backend \
  --tag us-central1-docker.pkg.dev/SEU_PROJETO/matterhorn-repo/matterhorn-api:v12

  2. Atualize a tag

    hclinfra/terraform.tfvars
    image_tag = "v12"

  3. Aplique

    bash
    cd infra
terraform plan    # deve mostrar só a troca de imagem
terraform apply

Deploy manual volta atrás no próximo apply. Um gcloud run deploy serve para testar rápido, mas o Terraform não fica sabendo. O próximo apply recoloca a tag que estiver no terraform.tfvars.

Se fizer um deploy manual, atualize o image_tag logo em seguida.

Voltar para uma versão anterior

As imagens antigas continuam no Artifact Registry. Coloque a tag anterior em image_tag e rode terraform apply. Para ver as tags disponíveis:

bash
gcloud artifacts docker tags list \
  us-central1-docker.pkg.dev/SEU_PROJETO/matterhorn-repo/matterhorn-api

Logs

Cada evento gravado gera uma linha Evento page_view salvo com sucesso!. Falhas aparecem como Erro ao inserir no BigQuery, seguidas do motivo.

bash
# Últimas 50 linhas
gcloud run services logs read matterhorn-backend --region us-central1 --limit 50

# Acompanhar em tempo real (comando beta, pode pedir um componente extra)
gcloud beta run services logs tail matterhorn-backend --region us-central1

No console, os mesmos logs ficam em Cloud Run › matterhorn-backend › Registros.

Custos e limites

  • Cloud Run escala até zero quando não há tráfego. O max_instance_count (3 por padrão) é o teto em picos.
  • Cada evento é uma requisição. O navegador pode fazer um OPTIONS antes, por causa do Content-Type: application/json.
  • BigQuery cobra o streaming insert por volume, com mínimo de 1 KB por linha, além de armazenamento e consultas. Os valores atuais estão na página de preços.

Segurança

O endpoint precisa ser público para receber eventos de navegadores, e isso tem consequências:

  • Qualquer pessoa com a URL consegue gravar eventos. Não publique a URL real em repositórios abertos.
  • Restringir o CORS a um domínio (parâmetro origins do CORS() no app.py) impede outros sites de enviarem pelo navegador, mas não barra um curl.
  • O papel bigquery.dataEditor vale para o projeto inteiro. Para limitar ao dataset, troque por google_bigquery_dataset_iam_member em iam.tf.
  • Não mande e-mail, CPF ou outros dados pessoais nos parâmetros.

Próximas melhorias

Ideias que ficaram fora da v1, na ordem em que fariam mais diferença:

  1. Particionar a tabela por data de ingestão, para baratear as consultas.
  2. Registrar no servidor o horário de recebimento, independente do relógio do visitante.
  3. ID de visitante e de sessão, para contar usuários.
  4. Enviar com navigator.sendBeacon, que sobrevive à troca de página.
  5. Evitar o preflight do CORS (enviando text/plain) ou cacheá-lo com max_age.
  6. Guardar o estado do Terraform num bucket do Cloud Storage.
